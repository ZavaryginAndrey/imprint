# W3 — Домен 2.0: День как проекция и дельта под UX

**Дата:** 2026-09-29 · **Статус:** дизайн согласован в чате, ждёт ревью спеки
**Фаза:** [W3-domain.md](../../../imprint2.0/W3-domain.md) · **Зависит от:** W2 · **Тег:** `web-w3`
**Не меняет:** [план tools](../plans/2026-09-28-web-tools.md) и [05-web-ux.md](../../../imprint2.0/05-web-ux.md) — заморожены;
расхождения закрываются новыми версиями tools (ниже)

## Зачем

Сервер сам вычисляет День — из строк, журнала и настроек пользователя, без телефона и без
мутирующего rollover, — а каждое правило UX §3–§5 становится tool. Тот же код даёт День в воркере,
в браузере (оптимистичный показ, ADR 003) и позже в MCP (W5).

**Успех:** `GET /api/state` + проекция дают День, совпадающий с телефоном v1 на тех же данных
(доказательство — перенесённые тесты домена v1); все действия UX — tools.

## Решения

| Вопрос | Решение | Почему |
|---|---|---|
| Как устроена проекция | **Чистая проекция в домене**; `location` — только намерение пользователя; tools спрашивают место задачи у той же проекции | Один День на сервере, в браузере и в MCP; нет таймера и флага `lastRolloverDayKey`. Отвергнуто: ленивый rollover v1 в объекте (мутация, браузер не предскажет), кэш-таблица Дня (YAGNI) |
| Шаги | **Чек-лист внутри задачи** (как мокап лендинга): шаги — строки `Task` с `parentId`, задача остаётся на месте. Конвейер цепочки и превращение задачи в группу уходят | Решение пользователя. Оверлей позже покажет разбитые задачи своим алгоритмом |
| Отметка шагов рутины | **По правилам родителя**: у одноразовой шаг помнит отметку, у рутины сбрасывается каждый день | Одно правило вместо двух; «последний шаг закрывает задачу» работает и для рутин |
| Прошедшая дата + «в бэклог» | **F5a**: дата — обещание, завтра задача сама вернётся в День. Шаг 16 сценария «три дня» правится в ADR 007 | Решение пользователя; не терять дату молча |
| `suggest_steps` | **Асинхронный серверный tool в воркере**, отдельный реестр; в MCP регистрируется вместе с `ALL_TOOLS` (W5). Чистые части (контекст, промпт, разбор, квота) — в домене | `runTool` домена остаётся синхронным и изоморфным (ADR 003) |
| Квота подсказок | **20 за логический день** на пользователя, константа домена | Разумный потолок для Gemini-ключа |
| Существующие тесты W0 | Меняются там, где поведение меняется по дизайну (список ниже), каждое — со ссылкой на ADR | Разрешено пользователем 2026-09-29 |

## W3a — День как проекция

### Настройки пользователя

```ts
interface UserSettings {
  timezone: string;     // IANA, по умолчанию "UTC"
  resetHour: number;    // 0–23, по умолчанию 4
  resetMinute: number;  // 0–59, по умолчанию 0
  language: "ru" | "en" // по умолчанию "ru"
}
```

- Хранятся в таблице `settings` (JSON, `id = 1`). `parseSettings(raw)` приводит любой JSON к
  `UserSettings`: неизвестные поля игнорируются, неверные значения → умолчания (P7). Пояс
  проверяется `Intl.DateTimeFormat`; неизвестный → `UTC`. Испорченные настройки никогда не дают 500.
- `ToolContext` получает `settings(): UserSettings` и `putSettings(s)` (пишет только
  `set_user_settings`).
- Tool `set_user_settings { timezone?, resetHour?, resetMinute?, language? }` — заплатка: не
  переданные поля не меняются, то же значение → `same_value`, неизвестный пояс → `invalid_input`.
  Запись идёт в той же транзакции, что `rev + 1`, и рассылается по сокету. Tool
  `get_user_settings` отдаёт настройки и `today`.
- `GET /api/state` отдаёт настройки как они сохранены (`{}` у нового пользователя); клиент приводит
  их тем же `parseSettings`, поэтому умолчания на сервере и в браузере совпадают.
- Веб при первом входе без заданного пояса вызывает `set_user_settings` с поясом браузера — это W4.

### Модуль `time/`

Чистые функции; пояс всегда явный, «местного» времени рантайма нет.

| Функция | Что делает |
|---|---|
| `logicalDayKey(at, s)` | Дата настенного времени `at` в `s.timezone`; если `at` раньше `dayStart` этой даты — предыдущая. Порт `LogicalDay.dateOf`; сравниваются моменты, поэтому в «повторе» часа день не откатывается назад |
| `dayStart(key, s)` | Момент `key` в `reset` по поясу — начало логического дня. Порт `logicalDayStart` |
| `dateStart(key, s)` | Полночь даты в поясе — кодировка `dueDate` (как `DueDates.startOfDay` v1) |
| `dueKey(millis, s)` | Дата, чья полночь ближе всего к `millis` (дата от `millis + 12 ч`) — смена пояса не сдвигает даты |
| `addDays(key, n)`, `weekday(key)` | Арифметика по `YYYY-MM-DD` через UTC |

- Переход на летнее время: `reset` в «дыре» → первый существующий момент после неё; в «повторе» →
  первый из двух.
- `dayKey` событий не пересчитывается (решение №17). Смена `resetHour` или пояса сразу меняет только
  аргумент `today` проекции. Отличие от v1 (там — со следующего сброса) фиксирует ADR 007.

### Контексты

- `sqlContext`: `todayKey = logicalDayKey(now, settings)`; UTC-заглушка W2 уходит.
- `memoryContext`: новые опции `settings` и `clock` (настенные часы, читаются при каждом `now()`);
  `todayKey` вычисляется, прямой `todayKey` по-прежнему принимается. Умолчания — пояс хоста и сброс
  в 00:00, поэтому `dateStart`/`dayStart` совпадают со старым `startOfDayMillis` и тесты W0 без
  изменения поведения остаются зелёными. Сервер по умолчанию — `UTC`, 04:00.
- `startOfDayMillis` и `todayDayKey` остаются в `compose.ts`/`completion.ts` ради существующих
  тестов; tools их не используют (тест на импорты в `tools/`).

### Правила проекции

**Время ничего не пишет, действия пишут.** Явное действие (`move_to_day`, дата «сегодня или
раньше», «в бэклог») пишет строку и событие, как v1. Всё, что делал сброс v1, вычисляется.

**Сворачивание журнала** — порт `Completion.of`, порядок `(at, deviceId, id)`:

| Кто | Чем решается «сделано» | Состояния |
|---|---|---|
| Одноразовая | последний `DONE`/`UNDONE` **за всё время** | `doneToday`: `DONE` с `dayKey ≥ today`; **завершена**: `DONE` с `dayKey < today` |
| Повторяющаяся | последний `DONE`/`UNDONE` **за `today`** | только `doneToday` |
| Шаг | по правилу родителя | шаг одноразовой хранит отметку, шаг рутины — на день |

**Шаг** (вводится в W3b, до этого проекция повторяет v1 и `parentId` не читает) — строка с
`parentId`, указывающим на существующую строку. В списках он не бывает отдельной строкой:
вкладывается в родителя. Удалённый родитель скрывает свои шаги. Цепочки v1 (родитель удалён)
приводит к этой форме импорт W7.

**День** — живые задачи верхнего уровня, не завершённые, по одному из правил:

| Вид | Условие | Ключ сортировки |
|---|---|---|
| `row` | одноразовая, `location = DAY` | `enteredDayAt ?? createdAt` |
| `due` | одноразовая, `location = BACKLOG`, `dueKey(dueDate) ≤ today`, нет `MOVED_TO_BACKLOG` за `today` | `dateStart(dueKey(dueDate))` |
| `appearance` | повторяющаяся (любой `location`): по каденции `weekday(today)` и `startDate` пуст или `dueKey(startDate) ≤ today`, **либо** притянута; последнее из `SKIPPED`/`PULLED_TO_DAY` за `today` — не `SKIPPED` | `dayStart(today)` |

- F4/F4b/F5: просроченная дата встаёт выше всего сегодняшнего и копится. F5a: «в бэклог» ставит
  `BACKLOG` и пишет `MOVED_TO_BACKLOG`, дата сохраняется; завтра правило `due` возвращает задачу.
- `SKIPPED`/`PULLED_TO_DAY` — побеждает последнее (в v1 притягивание удаляло пропуск).
- DB-3: удалить события нельзя, поэтому `set_repeating` при **включении** повтора (одноразовая →
  рутина) дописывает за `today` компенсирующие `UNDONE` (если было `doneToday`) и `PULLED_TO_DAY`
  (если был `SKIPPED` и новая каденция включает сегодня). Смена дней у рутины событий не дописывает.
- Решение №15 (порт v1): выключение повтора у рутины, отмеченной сегодня, делает её строкой Дня
  (`DAY`, `enteredDayAt = now`), чтобы отметка не пропала из-под пальца.

**Порядок Дня** — порт `buildDay` v1: якорь кластера группы (минимальный ключ её задач в Дне) ↑,
`groupId`, ключ ↑, `createdAt` ↑; выполненные стабильно вниз.

**Бэклог** — живые задачи верхнего уровня не в Дне и не завершённые, плюс **все** определения рутин
(рутина — появлением в Дне и определением в Бэклоге, как v1). Отмеченная сегодня задача бэклога
остаётся зачёркнутой и опускается в конец секции; после сброса скрывается. Секции по
`groups.position`, внутри `position ↑`, `createdAt ↑`.

**Форма результата:**

```ts
DayItem     = Task & { kind: "row" | "due" | "appearance", doneToday, sortKey, steps: StepView[] }
BacklogItem = Task & { doneToday, steps: StepView[] }
StepView    { task, done }                        // steps пусты до W3b
BacklogView { groups: { group, tasks: BacklogItem[] }[], ungrouped: BacklogItem[] }
locate(state, taskId, today, s): { place: "day" | "backlog" | "completed" | "hidden", kind }
```

Элементы плоские (поля задачи плюс вычисленные): агенту и UI так проще, а форма `list_backlog`
остаётся прежней. `projectDay`, `projectBacklog`, `locate` — в `packages/domain/src/day/`.
`list_day` возвращает `{ tasks: DayItem[] }`, `list_backlog` — `BacklogView`.

### «Хвост» журнала

Правило «завершена» читает последнее событие отметки, которое может быть старше окна в 35 дней.
`SqlStore` при пробуждении грузит окно **плюс** последнее `DONE`/`UNDONE` каждой задачи до окна
(`ROW_NUMBER() OVER (PARTITION BY taskId ORDER BY at DESC, deviceId DESC, id DESC)`); миграция 2
добавляет индекс `events(taskId)` (колонки групп — миграция 3 в W3b). `snapshot()` отдаёт окно + «хвост», вычисленные из памяти
(долгоживущий объект копит события после пробуждения). Браузер получает ту же картину.

### Существующие tools на проекции

- `move_to_day`: рутина — `PULLED_TO_DAY`, если сегодня последним уже не было `PULLED_TO_DAY` (как
  v1, без проверки каденции); отказ `skipped_today` уходит — притягивание после пропуска разрешено.
  Одноразовая вида `row` — `already_in_day`; вида `due` — становится явной строкой Дня на том же
  месте (`enteredDayAt = dateStart` её даты, как перенос v1); из бэклога — как раньше.
- `move_to_backlog` решает по `locate`: рутина не в Дне → `already_in_backlog`, иначе `SKIPPED`;
  одноразовая `row` → строка в бэклог + `MOVED_TO_BACKLOG`; `due` → только `MOVED_TO_BACKLOG`.
- `set_done`: одноразовая сравнивается с `doneToday` проекции. Конвейер (`promoted`) пока остаётся —
  он уходит в W3b вместе с моделью шагов.
- Даты в tools — через `dateStart`/`dueKey` с поясом пользователя.

## W3b — дельта под UX

### Группы

- **Миграция 3:** `groups.colorKey TEXT`, `groups.icon TEXT`. Тип: `colorKey: GroupColorKey | null`,
  `icon: GroupIconKey`. Старая строка читается как `colorKey` по таблице v1 (UX §5) или `null`,
  `icon = "tag"`.
- `color` (ARGB) **только выводится** из `colorKey`: базовый тёмный тон ключа (`amber` →
  `0xFFE0A34A`); `null` → `0`. Android v1 рисует любой ARGB; импорт W7 распознаёт и эти значения,
  и таблицу v1.
- Константы домена: `GROUP_COLORS` (8 ключей, тёмный и светлый тон по UX §5), `GROUP_ICONS`
  (16 ключей Phosphor). Тест контраста WCAG ≥ 3:1: тёмные тона к `SideBg #232A4B`,
  `DarkSurface #1C1F27`, `MetaSurface #343D63`; светлые — к `DaySurface #F7F5F1`, `DayBg #E2E6EC`.
- `palette.ts` (палитра v1) остаётся для импорта W7.

| Tool | Поведение |
|---|---|
| `create_group {name, colorKey?, icon?}` | Цвет — следующий по кругу после цвета последней живой группы по `position`; первой — `amber`. Иконка — `tag` |
| `set_group_color {groupId, colorKey}` | Заменяет `recolor_group` |
| `set_group_icon {groupId, icon}` | Новый |
| `delete_group {groupId}` | Удаляет сразу; живые задачи группы получают `groupId = null` с `updatedAt` = `deletedAt` группы. Результат `{group, detached}` |
| `restore_group {groupId}` | Снимает удаление и привязывает задачи с `groupId = null` и `updatedAt == deletedAt` группы (отвязанные этим удалением и не тронутые после). Без состояния — отмена работает и у агента |
| `reorder_groups {groupIds}` | Полный порядок живых групп → `position` 0..n−1. Другой набор id → `invalid_input`; тот же порядок → `same_value` |
| `list_groups` | + `colorKey`, `icon`, `openCount` (открытые задачи) |

`rename_group`, `set_group_collapsed`, `set_task_group` — без изменений.

### Задачи

| Tool | Поведение |
|---|---|
| `capture_task {title, view, groupId?, date?}` | Новый, для UI; таблица UX §3. `view`: `"day"` (десктоп «Все задачи», мобильный День), `"backlog"` (мобильный экран «Все задачи»), `{group: id}`. Дата `≤ today` = без даты. Группа — из `groupId` (чип; `null` — явное «Без группы»), иначе из `view`. См. таблицу ниже |
| `add_task {title, where, …}` | Остаётся для агента (W0) |
| `move_task {taskId, to, filterGroupId?}` | Новый, перетаскивание UX §4. `to: "backlog"` — как `move_to_backlog` + группа из `filterGroupId`. `to: "day"` — одноразовая: `DAY`, **дата снимается**, `enteredDayAt = now` (встаёт внизу, D10), группа сохраняется, `MOVED_TO_DAY`; рутина — `PULLED_TO_DAY` |
| `move_to_day` / `move_to_backlog` | Остаются (свайп телефона, дата сохраняется) |
| `set_due_date` | + UX §4: будущая дата у задачи в Дне → `BACKLOG`, `MOVED_TO_BACKLOG` |
| `set_repeating` | + компенсирующие события DB-3 |

Размещение `capture_task`:

| `view` | Без даты | С датой (> today) |
|---|---|---|
| `"day"` | День, группа = чип ?? нет | Бэклог с датой, группа = чип ?? нет |
| `{group: G}` | Бэклог, группа = чип ?? G | Бэклог с датой, группа = чип ?? G |
| `"backlog"` | Бэклог, группа = чип ?? нет | Бэклог с датой, группа = чип ?? нет |

### Шаги

- Проекция начинает вкладывать шаги (правило «Шаг» в W3a); конвейер `set_done` (`promoted`) уходит.
- `add_steps {taskId, steps}` заменяет `split_task`: шаги в конец (`position` после последнего),
  родитель на месте. Пустые строки отбрасываются; ничего не осталось → `empty_steps`.
- Шаг — обычная задача: `rename_task`, `delete_task`, `restore_task`, `set_done` работают как есть.
  Инструменты места (`move_*`, `capture_task`, `set_due_date`, `set_repeating`, `set_task_group`,
  `add_steps`) на шаге → `reason: "is_step"`. Вложенность — один уровень.
- **`syncParent`** — после `set_done` на шаге, `add_steps`, `delete_task`/`restore_task` на шаге:
  есть ≥ 1 живой шаг, все сделаны, родитель нет → `DONE` родителю; сделаны не все, родитель
  отмечен → `UNDONE`. Отметка самого родителя шаги не трогает. Результат несёт `parent: {id, done}`.

### Серверные tools (воркер)

```ts
interface ServerToolDef { name; description; input: ZodObject; run(deps, input): Promise<ToolResult> }
// deps: { state(): MergedState; settings(); today(); quota: QuotaStore; generate(prompt): Promise<string> }
```

- Реестр `SERVER_TOOLS` в `apps/worker/src/tools/`. `UserStore.callTool` ищет имя сначала в нём,
  потом вызывает `SqlStore.execute`. Маршрут `POST /api/tools/:name` не меняется (сессия, `Origin`,
  лимит тела).
- **`suggest_steps {taskId}`** → `{steps, remaining}`, ничего не пишет:
  1. `not_found` / `is_step`;
  2. **резерв** слота квоты в `meta` (`suggest:<dayKey>`) до вызова — пока ждём `fetch`, объект
     пропускает другие запросы; при сбое слот возвращается;
  3. `generate(buildStepsPrompt(stepsContext(state, taskId)))`, затем `parseSteps`.
- В домене: `stepsContext` (название, имя группы, до 15 последних сделанных в группе по журналу,
  уже существующие шаги), `buildStepsPrompt` и `parseSteps` (порт `CloudSplitPrompt`),
  `SUGGEST_DAILY_QUOTA = 20`.
- `gemini.ts`: `fetch` к `…/models/gemini-3.6-flash:generateContent`, ключ `GEMINI_API_KEY`
  (wrangler secret, `.dev.vars`). Нет ключа → `unavailable`; не 2xx или таймаут 15 с → `upstream`.
  Квота исчерпана → `reason: "quota"`. Квота не меняет `rev` и не рассылается.

### Результаты и ошибки

Tools не бросают исключений. Новые `Reason`: `is_step`, `quota`, `completed`. Новые `ToolError`: `upstream`,
`unavailable`.

### Уточнения W3b после W3a (2026-09-29)

Решены в чате после закрытия W3a; закрывают хвосты ревью W3a, отнесённые к W3b.

- **Завершённая задача** (проекция: `completed`) в `move_task`, `move_to_day`, `move_to_backlog`,
  `set_due_date`, `add_steps` → `reason: "completed"`, ничего не пишется. Вернуть её — `UNDONE` из Истории
  (W6), явное действие. Удалённая — по-прежнему `not_found`.
- **Поля группы необязательны в типе:** `colorKey?: GroupColorKey | null`, `icon?: GroupIconKey`. Снимки v1 и
  старые строки их не несут (P7). `groupLook(g)` нормализует: `colorKey` — если задан, иначе ключ по таблице
  v1 из ARGB (UX §5), иначе `null`; `icon ?? "tag"`. Tools и `list_groups` отдают нормализованные значения;
  новые и изменённые группы пишутся с обоими полями. Существующие литералы групп в тестах не меняются.
- **`list_groups`:** `taskCount` остаётся как был (живые строки группы), добавляется `openCount` — задачи
  верхнего уровня группы, которые проекция держит в Дне или Бэклоге и которые не отмечены сегодня; шаги не
  считаются.
- **Модель Gemini** — константа в `apps/worker/src/tools/gemini.ts`; идентификатор из спеки сверить с
  документацией Gemini перед первым деплоем.
