# Imprint Web Platform — новая карта 2.0

**Дата:** 2026-09-28 · **Статус:** дизайн согласован в чате, ждёт ревью спеки
**Заменяет:** структуру фаз `imprint2.0/00…07` (KMP-`core` для всех клиентов)
**Не меняет:** [план tools](../plans/2026-09-28-web-tools.md) и [UX веба](../../../imprint2.0/05-web-ux.md) — заморожены

## Зачем

План 2.0 строился на одном Kotlin Multiplatform-ядре для Android, веба и сервера: SQLDelight,
журнал операций с HLC, Firestore, Ktor в Cloud Run и переписанный Android. Курс меняется:

- **фокус — веб-платформа**;
- **рабочее Android-приложение v1 остаётся отдельным кодом** и живёт своей жизнью (Room + Drive,
  включая текущий этап 5.3b);
- позже Android подключается к работающей платформе и обменивается с ней данными, **код остаётся
  разным**.

**Успех:** многопользовательская веб-платформа, где все действия Imprint — это tools одного реестра
на сервере; веб-UI по `05-web-ux.md` работает поверх них, Claude подключается к тем же tools через
MCP, а Android может подключиться позже, не меняя модель данных платформы.

## Решения

| Вопрос | Решение | Почему |
|---|---|---|
| Источник правды | **Сервер — хаб.** Tools исполняются на сервере; веб-UI, агенты и позже Android ходят в один каталог. Drive в новой платформе не используется | Одна точка правил; MCP — тонкая обёртка над тем же реестром |
| Офлайн веба | **Оптимистичный онлайн.** Без сети — последнее состояние из кэша только на чтение | Веб — это стол с интернетом; офлайн-запись нужна телефону, не вебу |
| Пользователи | **Многопользовательская с первого дня**: вход через Google, изоляция данных, удаление аккаунта, квоты | Добавлять это позже дорого |
| Стек | **Cloudflare Workers + Durable Object на пользователя** | Синхронный SQLite-API объекта совпадает с синхронным `ToolContext`; запросы пользователя сериализуются — гонок нет; hibernatable WebSocket; готовые `McpAgent` и OAuth-провайдер для MCP |
| Модель данных | **Строки v1** (`tasks`, `groups`, `events` по `types.ts`; события только добавляются) + **День как проекция на TS** | План tools уже пишет эти строки; импорт v1 и мост Android — те же формы. HLC не нужен: объект сериализует записи |
| Где код | **Этот репозиторий, npm-workspace `platform/`**. `web/` замораживается как Drive-верстак | Знания (`docs/knowledge`) и контракт с Android — в одном месте, код раздельный |
| UI | **React 19 + Vite** (dnd-kit, Radix) | UX требует перетаскивания, поповеров, роутинга; самая богатая экосистема без слоёв совместимости |
| Мост Android | **Решается в начале W7** (синхронизация строк или вызовы tools) | Строки с LWW по `updatedAt` и журнал только на добавление оставляют открытыми оба пути |
| Переход | **С чистого листа.** Разовый импорт данных v1 — внутри W7 | До моста списки раздельны |
| Порядок | **UI (W4) раньше MCP (W5)** | Решение пользователя |

## Архитектура

```
platform/
  packages/domain/   чистый TS без Cloudflare: types, merge, completion, recurrence, compose, edit,
                     tools/*, time/ (логический день), day/ (проекция Дня), палитра и иконки групп
  apps/worker/       Hono-роутер + Durable Object UserStore (один на пользователя) + статика веба
  apps/web/          React + Vite
  docs/adr/
```

`packages/domain` не зависит ни от Cloudflare, ни от DOM: те же tools работают в воркере, в браузере
(оптимистичный показ) и в тестах на Node.

### Вызов tool от начала до конца

1. Нажатие в UI. Store прогоняет **тот же `runTool`** на `memoryContext` поверх последнего состояния с
   сервера и сразу показывает результат. Отдельной логики предсказания в UI нет.
2. `POST /api/tools/:name` с сырым входом. Воркер проверяет сессию и направляет запрос в
   `UserStore(idFromName(userId))`.
3. В объекте: `sqlContext.state()` — из памяти объекта, после пробуждения — из SQLite. `run`
   выполняется; записи копятся в буфере и фиксируются одной `transactionSync`, `meta.rev` растёт на 1.
   Если `run` бросил исключение — ничего не записано, результат `storage`.
4. Ответ — `{ result: ToolResult, rev }`; клиент перечитывает `GET /api/state`, если `rev` ушёл дальше ожидаемого. Объект рассылает `{ changed, rev }` по hibernatable
   WebSocket остальным подключениям пользователя.
5. Клиент заменяет предсказание состоянием с сервера. Если сервер отказал там, где локально было
   `changed: true`, или сеть упала — откат предсказания и тихая плашка «Не сохранилось · Повторить».

### Хранилище объекта

- Таблицы `tasks`, `groups`, `events` — колонки один к одному с `types.ts`; `settings` (`UserSettings`
  одной строкой); `meta` (`schemaVersion`, `rev`, квоты).
- Миграции — по `schemaVersion` при пробуждении объекта, каждая с тестом. Удаление колонок — только
  отдельным релизом (DB-1).
- `GET /api/state` отдаёт задачи, группы, настройки и события за окно, нужное проекциям (35 дней);
  история глубже — отдельным запросом в W6.

### Время (P5)

- `now()` — часы сервера, монотонно (как `monotonicClock` из плана tools).
- `todayKey()` — логический день от `UserSettings.timezone` и `resetHour`. Клиент время не присылает.
- Клиентский `memoryContext` для оптимистичного показа берёт пояс и `resetHour` из тех же настроек и
  ту же функцию из `time/`, поэтому ключ дня совпадает с серверным.

### Вход и сессии

- Google OAuth (authorization code + PKCE) в воркере; `userId` = Google `sub`.
- Сессия — подписанная cookie (`HttpOnly`, `Secure`, `SameSite=Lax`); секрет — в wrangler secret.
- В W5 тот же вход оборачивается OAuth-провайдером Cloudflare для MCP-клиентов.
- Удаление аккаунта: `DELETE /api/account` → `deleteAll()` в объекте пользователя.

### Gemini

`suggest_steps` — tool, который в воркере вызывает Gemini. Ключ хранится в wrangler secret и не
попадает на клиент; дневная квота на пользователя — в `meta` объекта.

### Окружения (P8)

`wrangler dev` работает локально на Miniflare; отдельные воркеры `imprint-dev` и `imprint-prod` со
своими Google OAuth-клиентами и секретами. Разработка никогда не касается данных prod.

## Ошибки

| Случай | Поведение |
|---|---|
| Отказ правила или ошибка входа tool | HTTP 200 с `ToolResult` (`changed: false, reason` или `ok: false, error`) — как в плане tools |
| Нет сессии | 401 → веб уводит на вход; ожидающие вызовы повторяются после входа |
| Сеть недоступна | Откат предсказания, тихая плашка «Не сохранилось · Повторить»; без спиннеров на основных экранах |
| Ответ с `rev` ≤ уже виденного клиентом | Игнорируется (гонка между вкладками) |
| Сбой хранилища в объекте | Транзакция не фиксируется, `ToolResult` `storage` |

## Тесты

- `packages/domain` — Vitest на Node. Тесты, скопированные из `web/`, не меняются.
- `apps/worker` — `@cloudflare/vitest-pool-workers`: настоящий DO с SQLite; изоляция пользователей,
  атомарность вызова, рост `rev`, миграции.
- `apps/web` — Vitest для store; Playwright по критериям UX §8.
- CI (GitHub Actions): typecheck, тесты всех трёх пакетов, сборка; деплой в prod — только по тегу.

## Риски

- **Часовой пояс до W3a.** `startOfDayMillis` из `compose.ts` считает «местное» время, а в Workers это
  UTC. До W3a даты на сервере — по UTC; W3a заменяет это модулем `time/` с явным поясом.
- **Рост журнала на клиенте.** Страховка — окно событий в `GET /api/state`, история отдельным запросом.
- **Расхождение копий домена** `web/` и `platform/`. Страховка — `web/` официально заморожен после W0.
- **Новая платформа.** W1 заканчивается живым деплоем «hello DO» в dev до какой-либо логики.
- **Мост Android без выбранного механизма.** Модель данных платформы не должна его закрывать: строки
  с `updatedAt`, события с `id` и `dayKey`, никаких серверных мутаций «сами по себе».
