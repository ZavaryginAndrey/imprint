## 1. Что за продукт

**Внешняя память для дел, а не помощник продуктивности.**
Позиционирование: «я подхвачу то, что ты роняешь». Аудитория — узко, люди с СДВГ-паттернами

проектируем от неё, включена по умолчанию, отказ тихо откатывается на уведомление.

## 3. Фундамент — делается ДО первой фичи

### 3.1 Debug-сборка со своим applicationId ⭐

```kotlin
debug { applicationIdSuffix = ".debug" }
```
Debug и release живут на телефоне параллельно; `pm clear` на debug не трогает боевые данные.
Это лечит **причину** потери истории, а не последствие.

### 3.2 Схема, готовая к синхронизации ⭐⭐ — самое важное решение

Синхронизация (§7) задним числом не прикручивается: она требует полей, которых в схеме потом
не будет. Пустая схема — единственный дешёвый момент их заложить. **Реализовывать синхронизацию
в v1 не надо; надо не закрыть себе дверь.**

```
tasks(
  id: String UUID,                       ← не autoincrement
  title, location, dueDate, startDate, groupId, isRepeating,
  recurrenceMask, priority, parentId, position, createdAt, enteredDayAt,
                  ↑ всегда 0 в v1 (§8.1)                   ↑ ключ сортировки Дня (§4.2.1)
  updatedAt: Long,                       ← last-write-wins по текущему состоянию
  deletedAt: Long?                       ← tombstone, не физическое удаление
)                                        ← НЕТ isDone, НЕТ completedAt (§4.2)

groups(id: String UUID, name, position, isCollapsed, color,
       createdAt, updatedAt, deletedAt?)

events(id: String UUID, taskId: String?, type, at, dayKey,
       title, groupId, isRepeating, surface?,
       deviceId: String)                 ← origin, чтобы не переигрывать свои события
```

**Пять правил, вытекающих из этого:**

1. **UUID вместо autoincrement.** Два пира не могут независимо раздавать целые числа.
2. **Tombstones.** Удаление = проставить `deletedAt`, физической строки не убирать; UI фильтрует.
   Иначе на втором устройстве удалённая задача воскреснет. Бонус: undo при свайпе становится
   снятием флага вместо переинсерта — проще, чем было.
3. **`updatedAt` на каждой мутируемой строке.** Разрешение конфликтов по текущему состоянию
   (переименовали в двух местах) — last-write-wins.
4. **`deviceId` в событии.** Генерится один раз на установку. Нужен, чтобы пир не переигрывал
   собственные события и для тай-брейка при равных `at`.
5. **Журнал конфликтов не имеет** — он append-only, события просто складываются. Это и есть
   причина, по которой синхронизация вообще возможна без сервера.

*Прунинг tombstone'ов (через N месяцев) — задача сильно позже, не v1.*

### 3.3 Журнал событий — единственный источник истины о выполненности ⭐

**На строке задачи НЕТ `isDone`. И НЕТ `completedAt`.**

Задача выполнена в логическом дне `D` ⟺ последнее событие `DONE`/`UNDONE` для пары
`(taskId, D)` — это `DONE`. Правило **одинаково** для одноразовых и повторяемых задач.

Типы событий: `CREATED · DONE · UNDONE · MOVED_TO_DAY · MOVED_TO_BACKLOG · SURFACED · SPLIT ·
SHOWN · DELETED · SKIPPED`. Индексы: `taskId`, `dayKey`, `type`.

**Денормализация намеренная:** `title`, `groupId`, `isRepeating` копируются в событие при записи,
поэтому переименование или удаление задачи никогда не переписывает прошлое, а частота не
считается по текущей строке названия.

**Read-model:** экраны читают проекцию `TaskView(task, isDoneToday)` — Flow, собранный из двух
Room-потоков (задачи + сегодняшние события) в репозитории. Масштаб — десятки строк, отдельная
материализованная таблица не нужна. ⚠️ Два потока Room не синхронны — держать защиту от
дубликата id из `DayAssembly` (02-BUGS CMP-2).

**Что чинится структурно:** баг FUNC-2 (рассинхрон истории при отправке выполненной задачи
в бэклог) перестаёт существовать, а не затыкается. История и аналитика — одна проекция одного
источника. Данные под все шесть эпиков копятся с первого дня, без будущих миграций.

**Принимаемая цена:** каждый запрос списка тянет сегодняшние события; сортировка «выполненные
вниз» считается в Compose, а не в SQL.

### 3.4 Экспорт / импорт в файл ⭐

Локальный дамп через SAF (`ACTION_CREATE_DOCUMENT` / `ACTION_OPEN_DOCUMENT`), формат **JSON**.
Содержимое: задачи + группы + **полный журнал** + настройки.

**Импорт — слияние**, а не замена:
- События сливаются по `id` (append-only, конфликтов нет).
- Строки задач/групп — по `id`, побеждает больший `updatedAt`.
- Отсутствующее у импортёра — добавляется; `deletedAt` уважается.
- Перед импортом — автобэкап текущего состояния в соседний файл.

Слияние — не прихоть: это тот же алгоритм, который потом обслужит синхронизацию (§7).
Написать его один раз здесь дешевле, чем писать замену сейчас и слияние потом.

**Импорт не устаревает с появлением синхронизации** (решение №18). Синхронизация — этап 5
дорожной карты, после всех шести эпиков концепта (§9), то есть далеко впереди; до неё импорт —
единственная страховка данных. После неё — тоже: продукт заявляет «локально и офлайн» (§1),
а файл на диске работает без аккаунта и без сети, что облачная синхронизация в принципе дать
не может. Алгоритм слияния при этом не выбрасывается: это буквально тот же код, что потом
обслужит синхронизацию (§7).

**Устойчивость импорта:** весь импорт — одна транзакция Room; любая ошибка парсинга или
записи откатывает **всё целиком**, состояние приложения до импорта не тронуто. Автобэкап
(строка выше) уже снят до попытки, так что данные восстановимы в любом случае. Битый /
не-JSON файл — понятная ошибка пользователю, без частичного слияния.

## 4. Модель

### 4.1 Одна таблица + ортогональные оси

| Ось | Значения | Смысл |
|---|---|---|
| `location` | `DAY` / `BACKLOG` | где живёт задача |
| `dueDate` | millis / null | одноразовое всплытие в День |
| `isRepeating` + `recurrenceMask` | bool + 7 бит | повторяющееся определение |
| `startDate` | millis / null | якорь начала повтора (значим только для повторяемых) |
| `groupId` | UUID / null | **одна** группа: секция в Бэклоге, цветной лейбл в Дне (§8.1) |
| `parentId` | UUID / null | шаг разбитой задачи (под эпик 2) |
| `priority` | int | ручная закрепа под эпик 1. **В UI v1 не экспонируется, всегда 0** (§8.1) |

Никакой отдельной таблицы под бэклог. Никакой отдельной таблицы под вечер.

### 4.2 Сборка «Дня» (вычисляемая)

```
День = реальные строки location='DAY' и deletedAt IS NULL
     + появления повторяемых задач из бэклога, где:
         каденция включает сегодняшний день недели
       И startDate пуст или уже наступил
       И нет события SKIPPED за сегодняшний dayKey
       И id ещё не является реальной DAY-строкой
```

**Задача с `dueDate` попадает в День переносом, а не появлением** (решение №11, 2026-09-07):
при наступлении даты строка меняет `location` на `DAY`, в журнал идёт `MOVED_TO_DAY`, из Бэклога
она исчезает. Формула Дня остаётся из двух источников — `dueDate` третьего не добавляет.
Момент переноса: в ближайший сброс (§4.3), а если дата выставлена на сегодня или в прошлое —
**немедленно**, не дожидаясь сброса.

`enteredDayAt` при таком переносе = **начало логического дня `dueDate`**, а не момент сброса.
Отсюда: просроченная дата поднимает задачу выше по общему правилу §4.2.1 — ровно туда же, куда
встала бы задача, провисевшая в Дне столько же дней. Отдельного признака «просрочено», счётчика
дней и метки нет и не нужно: приоритет проступает сам, негласно.

`dueDate` при отправке задачи обратно в Бэклог (§6.3, `MOVED_TO_BACKLOG`) **не обнуляется**.
Значит для задачи с прошедшей датой «в бэклог» = отсрочка до конца дня: назавтра она вернётся
в День. Чтобы отложить бессрочно, дату снимают чипом. Это осознанно: дата — обещание, которое
инструмент не даёт тихо потерять.

Действия над появлением повторяемой задачи: **отметка** → `DONE(taskId, dayKey)`; **свайп
«не сегодня»** → `SKIPPED` («пропустить сегодня», определение цело); **правка названия** →
правит определение в бэклоге. Удалить повторяемую задачу совсем — только свайпом в Бэклоге,
с undo.

Повторяемая задача, отмеченная выполненной, остаётся в Дне отмеченной до сброса.

**Свайп в Дне — два направления** (решение №13, 2026-09-10). Жест «пропустить» на одноразовой
строке уже занят смыслом «не сегодня», а не «удалить», поэтому удаление получает отдельное
направление, а не перегружает первое:

| Направление | Одноразовая строка | Появление повторяемой |
|---|---|---|
| **«не сегодня»** | `MOVED_TO_BACKLOG` — уходит из Дня, `dueDate` не трогается (§4.2) | `SKIPPED` — пропуск на сегодня, определение цело |
| **«удалить»** | `deletedAt` + undo (как в Бэклоге, §3.2) | **недоступно** — строка после свайпа пружинит назад с подсказкой «удалить можно в Бэклоге» |

Оба направления доступны только у **невыполненных** строк — у выполненной любой свайп не
делает ничего: «в бэклог» запрещено инвариантом §6.3, а удалять выполненное молча — терять
историю дня из-под пальца.

**Ручного переноса повторяемой задачи в День вне каденции нет** (решение №14). В Бэклоге
у повторяемой задачи не появляется кнопки «в День»: каденция — единственный и достаточный
ответ на «когда», второй параллельный способ ответить на тот же вопрос не нужен — та же логика,
по которой отвергнут ручной приоритет (§8.1). Разово сделать задачу сегодня вне каденции —
значит завести отдельную одноразовую задачу или на время изменить саму каденцию.

**Выключение повтора у появления, уже отмеченного сегодня** (решение №15): задача становится
обычной одноразовой в Бэклоге. Сегодняшнее появление в Дне при этом **материализуется** —
получает `location=DAY` как реальная строка — и остаётся видимым отмеченным до конца дня;
без этого шага отметка пропала бы из-под пальца в момент, когда `isRepeating` уже `false`,
а появление вычисляется только для повторяемых определений. Прошлые события `DONE`/`SKIPPED`
в журнале не переписываются и продолжают считаться в истории.

### 4.2.1 Порядок в списках ⭐ (решение №9)

**День — плоский список, без секций.** Сортировка:

```
1. enteredDayAt  ↑    раньше попало в День — выше
2. createdAt     ↑    тайбрейк для попавших одновременно
3. выполненные   ↓    вниз (считается в Compose, §3.3)
```

`enteredDayAt` проставляется в момент попадания в День: у задачи, добавленной прямо в День, —
время создания; у перенесённой из Бэклога вручную — время переноса; у перенесённой по
наступившему `dueDate` — **начало логического дня этой даты** (§4.2, решение №11);
у появления повторяемой задачи — момент rollover.

Свойства, ради которых выбрано именно это:

- Задача, добавленная снизу через поле ввода, **остаётся снизу** — там, где её напечатали.
  Сортировка «никогда не показанные наверх» телепортировала бы её от места создания.
- Невыполненное со вчера имеет более ранний `enteredDayAt` и стоит выше — **бесшумный** кивок
  в сторону незакрытого: без счётчика дней, без значка, без упрёка.
- Строка не двигается сама. Порядок меняется только от действия пользователя — позиционная
  память работает.
- У повторяемых задач нет спецкейса: rollover раньше любого дневного добавления, поэтому они
  оказываются наверху по общему правилу, а не по привилегии.

**Ручного перетаскивания (drag & drop) в Дне нет** (решение №19). «Строка не двигается сама»
выше — это про автоматику, но правило шире: пользователь тоже не переставляет строки руками.
Порядок Дня — это история попадания задач в поле зрения, а не отражение того, что человек
сейчас считает важным; drag & drop был бы чёрным ходом к ручному приоритету, который §8.1
осознанно отложил до эпика 1 («пин появляется одновременно с эпиком 1, когда его смысл
объясняется одной фразой»). До тех пор порядок меняется только косвенно: отметкой,
переносом в бэклог и обратно, свайпом.

**Бэклог — секции групп** в порядке `groups.position`, внутри секции `position` ↑, тайбрейк
`createdAt`. Задачи без группы — отдельной секцией сверху.

**Принцип, из которого следуют оба правила:** Бэклог упорядочен **структурой** (поверхность
планирования), День — **вниманием** (поверхность делания).

### 4.3 Конец дня (rollover)

В час сброса (дефолт 4:00): выполненные одноразовые прунятся из активного списка (история —
в журнале), невыполненные копятся, **задачи бэклога с наступившим `dueDate` переезжают
в День** (`MOVED_TO_DAY`, `enteredDayAt` = начало логического дня их даты, §4.2),
повторяемые задачи появляются заново по каденции
и получают `enteredDayAt` = момент сброса (§4.2.1). Отдельной ветки для
«Вечера» больше нет. Пропущенный сброс догоняется при старте.

**`dayKey` не пересчитывается задним числом** (решение №17). Каждое событие в момент записи
вычисляет свой `dayKey` из **текущего локального времени устройства** и часа сброса,
действующего **на этот момент** — и это значение больше не трогается:
- смена часа сброса в Настройках влияет только на события **после** сохранения — уже
  записанные `dayKey` не переезжают, история не задним числом не меняется;
- перелёт в другой часовой пояс меняет, что устройство считает «сейчас», но прошлые события
  хранят тот `dayKey`, с которым были записаны; `LogicalDay.kt` работает с локальным временем
  без хранения исходной таймзоны события — синхронизация с этим уже совместима (§3.2:
  конфликтует только текущее состояние строки, а не append-only журнал).

## 5. Напоминания

### 5.1 Единая точка отбора

`domain/ReminderContent.select()` — 5 слотов. Ранжирование: ручной приоритет → никогда не
показанные → дольше всего не показывалось. Обе поверхности берут один и тот же набор.
Набор фиксируется в момент показа, освободившийся слот **не добивается**, плашка закрывается
когда сделано всё показанное.

**Источник отбора — исключительно невыполненные задачи сегодняшнего «Дня»** (решение №10,
2026-09-07). Бэклог в отбор не попадает никогда: бэклог — это «потом», а инвариант механизма —
не впечатывать то, к чему нельзя приступить прямо сейчас (01-CONCEPT §4). Следствия:
- чтобы задача начала впечатываться, она должна сначала оказаться в Дне — это единственный
  вход в механизм, и он под контролем человека;
- пустой или полностью выполненный День = **показа нет вообще** (не пустая плашка);
- «День» здесь — вычисленный список §4.2 целиком, включая появления повторяемых задач.

⚠️ **Эта цепочка — только для отбора в напоминание, не для сортировки списков (§4.2.1).**
Оверлей — *селектор*: берёт 5 из N и обязан ранжировать агрессивно. Список — *контейнер*:
показывает все N, и его работа — находимость и стабильность. `SHOWN` меряет показ в плашке,
а не просмотр в списке: если сортировать им список, строки начнут переставляться от события,
которого пользователь не совершал и не видит. При `priority = 0` у всех (§8.1) цепочка
вырождается в «никогда не показанные → дольше всего не показывалось» и работает как есть.

### 5.2 Выбор поверхности

`chooseReminderSurface(overlayEnabled, canDrawOverlays, deviceLocked)` — плашка только при
активном экране, иначе уведомление со списком (`InboxStyle`, `VISIBILITY_PRIVATE`: названия
появляются после разблокировки).

### 5.3 Три аларма

Каждый ресивер перевзводит свой следующий; плюс `BootReceiver`.

1. **Дневное** — фиксированный интервал в окне `[start, end]`, только при наличии невыполненного,
   минимум 15 мин.
2. **Вечернее** — один показ в заданное время (дефолт 22:00), **отбор отфильтрован по группе
   «Вечер»**. Слотами/ротацией не трогается. Это замена бывшей вкладки, а не отдельная подсистема.
   Привязка — по `id` группы, а не по названию: переименование её не ломает. Если группа удалена
   (что возможно только после того, как её опустошили, §8.1), вечернее напоминание молча
   ничего не показывает.
3. **Сброс дня** — час сброса, с догоном пропущенного.

**Запреты платформы соблюдать буквально** (02-BUGS §AND-1…AND-6): никакого foreground-сервиса,
никакого `USE_FULL_SCREEN_INTENT`, никакого `ACTION_USER_PRESENT`. `SCHEDULE_EXACT_ALARM` —
опционально, при отказе неточные; `USE_EXACT_ALARM` не брать.

## 7. Синхронизация (после v1.0)

**Модель: несколько равноправных пиров над общим хранилищем.** Пиры — телефоны и **собственная
веб-версия** приложения. Google используется как **точка соединения** (identity + хранилище),
а не как драйвер модели данных: никаких Google Tasks и Sheets, чужая модель без групп, повторов
и каденции не навязывается.

**Почему это будет работать:** журнал append-only + UUID + tombstones + `updatedAt` + `deviceId`
(§3.2). События не конфликтуют — складываются; конфликтует только текущее состояние строки —
решается last-write-wins. Алгоритм слияния тот же, что пишется для импорта файла (§3.4).

**Что решается позже, на код v1 не влияет:** транспорт (Drive `appDataFolder` / Firebase /
собственный бэкенд), схема аутентификации, офлайн-очередь, ритм синхронизации.
Веб-версия — отдельный проект, разделяющий модель.

**Что важно не забыть:** двусторонняя синхронизация тащит данные в облако, а концепт заявляет
«локально и офлайн». К моменту реализации формулировку в §1 и в маркетинге придётся честно
обновить — или сделать синхронизацию явным опциональным включением.

### 8.1 Решение №9 — группы, приоритет и порядок в списках (2026-09-07)

#### Группа — одна на задачу. Мульти-групп нет

- В **Бэклоге** группа — сворачиваемая секция (несущая структура планирования).
  В **Дне** — цветной лейбл под названием задачи, список плоский.
- **Цвет** задаётся при создании группы в Бэклоге; лейбл в Дне подхватывает этот цвет.
- В **плашке и уведомлениях** группы и лейблы не показываются вовсе.

**Удаление группы запрещено, пока она не пуста** (решение №12, 2026-09-07). Создание группы —
осознанное действие: человек заводит общее место для задач. Разрушение общего места симметрично
требует работы, а не одного свайпа. Действие «удалить» у непустой группы **задизейблено**
с нейтральным пояснением («в группе 12 задач — перенесите или закройте их»), без упрёка
и без предложения «удалить всё вместе».

- **«Пуста»** = нет ни одной живой (`deletedAt IS NULL`) задачи с этим `groupId`, **независимо
  от `location`**: задача группы, которая сейчас лежит в Дне, тоже держит группу непустой.
- Пустая группа удаляется свайпом с undo, как задача: `deletedAt` + снекбар (§3.2).
- Переименование и смена цвета не ограничены ничем — избавиться от неудачной таксономии
  можно, не удаляя.
- Каскадное удаление задач вместе с группой не существует ни в каком виде.

Почему не many-to-many:

1. **Ломает burndown эпика 3.** Задача в двух группах считается дважды, сильная зона маскирует
   слабую — ровно тот эффект, ради избегания которого суммарный прогресс и был отвергнут (01-CONCEPT §6).
2. **`groupId` в журнале денормализован скаляром** (§3.3). Множество потребовало бы join-таблицы
   со своими tombstones, `updatedAt` и разрешением конфликтов при синхронизации — мирить пиров
   пришлось бы не по строке, а по набору связей.
3. **Дубли строк в Бэклоге.** Одна задача в трёх секциях = три строки; свайпнул в одной — осталась
   в двух; счётчик «X из N» врёт; доверие к списку падает, а список — это внешняя память.
4. **Всё равно вырождается.** Many-to-many немедленно требует «основной» группы — для секции,
   для burndown, для слота оверлея (эпик 5). То есть на выходе «одна главная + метки», но
   реализованное самым дорогим способом.
5. **Цена решения при СДВГ.** «В какую группу?» — один выбор с естественным концом.
   «В какие группы?» — открытое множество без правила остановки, трение ровно в момент захвата,
   плюс таксономия становится полем для бесконечной наладки (продуктивное на вид избегание).

**Обратимость:** 1 → N мигрируется дёшево (join-таблица + бэкфилл единственной группой),
N → 1 разрушительно (какая из трёх выживет — решать некому). Начинаем с обратимого — та же
логика «не закрыть себе дверь», что в §3.2.

**Реальные пересечения** решаются по порядку дешевизны: переименовать/слить группы →
разбить на шаги (`parentId`, эпик 2) → плоские метки как **ортогональная** ось (только поиск
и фильтр, без секций и без участия в измерении) — не раньше, чем появятся данные, что это нужно.

#### Ручного приоритета в v1 нет

- `priority: int` остаётся в схеме и **всегда 0**. Дверь не закрыта, UI не тратится.
- Пин в концепте — **не механизм приоритизации, а предохранитель к эпику 1**: «частота
  переставляет только незакреплённое» (01-CONCEPT §8). Анализ частоты отложен, значит
  предохранителю нечего останавливать. Механизм без угрозы, от которой он защищает, лишний.
- Пин появляется **одновременно с эпиком 1**, когда его смысл объясняется одной фразой:
  «эта задача остаётся наверху, автоматика её не двигает».
- Что есть вместо: **когда** (`dueDate` + чипы) и **как часто** (каденция повтора). Оба вопроса
  имеют конкретный ответ, который человек знает. «Насколько это важно» ответа в момент захвата
  не имеет и порождает залипание.
- Когда пин вернётся, **лимита на количество не будет**: закрепа деградирует заметно
  (закрепил всё → порядок не изменился → бесполезность видна глазами), сторож не нужен.
  Тогда же: в Дне пин поднимает наверх списка, в Бэклоге — наверх своей секции.
- Пин `> 0` без движения — дополнительный входной признак для эпика 6 («сопротивляющаяся
  задача»), бесплатно. Авто-снятия пина не будет: тихо отменять решение человека противоречит
  принципу «решает человек, исполняет инструмент».

#### Порядок в списках

См. **§4.2.1**. Зафиксировано отдельно: **оверлей ранжирует, список — нет**; `SHOWN` не
используется для сортировки списка (§5.1).

#### Переименование по всей спеке

`isRoutine` → `isRepeating`, «рутина» → «повторяемая задача». Слово «рутина» осталось от
удалённой отдельной сущности (вкладка «Вечер», таблица `bedtime_items`) и стабильно читается
как «то, от чего отказались», хотя механизм — обычная задача с флагом повтора и каденцией,
интервал выбирает пользователь. Поля ещё не существует: переименование бесплатно сейчас и
стоит правок в коде, в JSON экспорта и в журнале событий потом.

## 10. Чего в продукте не будет

Стрики · очки · бейджи · уровни · любая геймификация · пуш «вернись» · награды за заходы ·
тренд «растёт/падает» в аналитике · метрики роста вовлечённости как цель · объявления о том,
что помощь снята.

Успех — когда пользователь **уходит**.
